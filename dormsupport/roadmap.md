# DormSupport — roadmap MVP

## Цель и границы MVP

Ответственный сотрудник создаёт аккаунты жильцов и выдаёт им первоначальные логин и пароль. Жилец входит в систему, создаёт заявку на ремонт и отслеживает её статус. Ответственный сотрудник работает с общей очередью заявок, переводит их в работу и закрывает. Администратор также имеет доступ к очереди и управлению статусами. Уведомления о создании и смене статуса приходят в закрытую Telegram-группу сотрудников.

Роли:
- **ADMIN** — создаёт аккаунты пользователей, имеет доступ к общей очереди заявок и управлению статусами.
- **RESIDENT** — создаёт заявки и видит только собственные.
- **REVIEWER** — видит все заявки и меняет статусы.

Статусы: `NEW → IN_PROGRESS → CLOSED`. Самостоятельной регистрации нет: аккаунты создаёт ADMIN. После входа каждый пользователь получает личный кабинет в зависимости от роли.

Технические решения для реализации:
- Identity, Issues и Notifications имеют отдельные PostgreSQL БД.
- Frontend обращается к сервисам только через Gateway.
- Issues публикует события в **Kafka**; Notifications отправляет сообщения в Telegram.
- В MVP используются серверные сессии без JWT. Идентификатор сессии имеет тип `UUID` и передаётся в заголовке `X-Session-Id`.
- Диаграммы — исходники **Mermaid `.mmd`** и сгенерированные **`.png`**.
- Документация хранится в `dorm-support-documents`, подключённом к infrastructure как submodule.
- Swagger содержит описания, схемы и ограничения, но без явно заданных `example` / `examples`.

Это план целевого MVP, а не отчёт о готовых функциях. Наличие операции в Swagger не означает, что она уже реализована. Расхождения текущих требований и контрактов с решениями выше устраняются на этапе 0 в отдельных задачах.

## Последовательность работ

| Этап | Содержание | Результат |
|---|---|---|
| 0 | Контракты, ERD, диаграммы, завершение дизайна | Согласованный API и готовые макеты |
| 1 | Identity / Auth | Создание аккаунта ADMIN, вход, серверные сессии, текущий пользователь и выход |
| 2 | Issues и тестирование | Создание, список, права и жизненный цикл заявки |
| 3 | Kafka и Notifications | События, сохранение уведомлений, Telegram и техническое логирование |
| 4 | Gateway и интеграционное тестирование | Все сервисы работают через единую точку входа |
| 5 | Frontend и тестирование | Готовый пользовательский интерфейс по ролям |
| 6 | Сквозная проверка и подготовка сдачи | Воспроизводимый запуск и демонстрация MVP |

Макеты выполняются в начале. После согласования контрактов frontend можно разрабатывать параллельно backend, используя моки. Базовую маршрутизацию Gateway и Docker Compose стоит подготовить заранее; этап 4 — завершение интеграции и её проверка. Календарные сроки и ответственные назначаются после определения даты сдачи и доступности команды.

## Этап 0. Контракты, документация и дизайн

### Задачи
- Согласовать роли и правила доступа для каждой операции.
- Привести общий OpenAPI, Swagger сервисов и Gateway к одним путям, моделям и ошибкам.
- Описать создание аккаунтов администратором с первоначальными логином и паролем.
- Описать вход, выход, получение текущего пользователя и серверные сессии через `X-Session-Id`.
- Описать UUID как `type: string` + `format: uuid`. Не заменять все бизнес-ID на UUID автоматически.
- Убрать явно заданные примеры Swagger, сохранив описания и ограничения полей.
- Обновить ERD: добавить серверные сессии, уточнить обязательность и кратности связей, не обозначать межсервисные ссылки как SQL FK.
- Синхронизировать схемы Kafka-событий между документацией, Issues и Notifications.
- Обновить архитектурную и сценарные диаграммы под Kafka, серверные сессии и авторизацию.
- Завершить макеты: создание пользователя ADMIN, вход, личный кабинет жильца, создание заявки и очередь ответственных сотрудников.
- Предусмотреть в макетах загрузку, пустые списки, ошибки, мобильное отображение и запрет доступа.

### Проверка и критерий готовности
OpenAPI проходит валидацию; контракты сервисов согласованы. Для каждого основного сценария есть экран и API-операция. Все диаграммы имеют актуальные исходники и изображения. Замечания, видимые на скриншотах Miro, учтены; макеты согласованы командой.

## Этап 1. Identity / Auth

Публичные операции имеют префикс `/api/v1`.

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `POST /admin/users` | Создать аккаунт пользователя и первоначальные учётные данные | ADMIN |
| `POST /auth/login` | Проверить логин и пароль и создать сессию | Публичный endpoint |
| `POST /auth/logout` | Отозвать текущую сессию | По `X-Session-Id` |
| `GET /auth/me` | Получить свой профиль | Любая активная роль |

Внутренняя операция проверки сессии доступна только сервисам и не публикуется через Gateway. Она возвращает `userId`, роль и данные проживания, необходимые Issues Service.

### Задачи
- Создать таблицы пользователей и сессий отдельным SQL-файлом для `identity_db`, подключённым через Docker Compose.
- Добавить начального ADMIN при заполнении `identity_db`.
- Разрешить ADMIN создавать пользователей с ролями `RESIDENT` и `REVIEWER`; создание ADMIN через публичный API не разрешать.
- Хешировать пароли через BCrypt и не записывать пароли или session ID в логи.
- Создавать сессию с UUID после успешного входа.
- Проверять срок действия и отзыв сессии.
- Реализовать проверку ролей и единый формат ошибок.
- Передавать `X-Session-Id` через Gateway во внутренние сервисы.

### Тестирование и результат
Проверить создание пользователя ADMIN; дубликат логина; некорректные данные; попытку создать ADMIN; вход с первоначальным паролем; неверный пароль; успешный вход; истёкшую и отозванную сессию; получение текущего пользователя; выход; доступ к внутренней операции без разрешения.

**Готово, когда:** ADMIN создаёт аккаунт, пользователь входит и выходит из системы, а сервисы могут определить пользователя и его роль по активной сессии.

## Этап 2. Issues + тестирование

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /categories` | Категории неисправностей | RESIDENT, REVIEWER, ADMIN |
| `POST /issues` | Создание заявки | RESIDENT |
| `GET /issues` | Общий список и фильтрация | RESIDENT — свои; REVIEWER и ADMIN — все |
| `GET /issues/{issueId}` | Детали заявки | RESIDENT — свои; REVIEWER и ADMIN — любые |
| `PATCH /issues/{issueId}/status` | Смена статуса | REVIEWER и ADMIN |

Жилец может открыть только собственную заявку. REVIEWER и ADMIN могут открыть любую заявку из общей очереди.

### Задачи
- Создать таблицы отдельным SQL-файлом для `issues_db`, подключённым через Docker Compose.
- Проверять активную сессию и роль через внутренний Identity API.
- Получать проживание через внутренний Identity API; сохранять снимок комнаты и корпуса.
- Атомарное создание заявки в статусе NEW и первой записи истории.
- Выдача списка с фильтрами по статусу, пагинацией и корректным `total`.
- Разделять доступ к списку: собственные заявки для RESIDENT и общая очередь для REVIEWER/ADMIN.
- Переходы `NEW → IN_PROGRESS → CLOSED`, проверка `expectedStatus`, защита от конкурентных изменений.
- Повтор уже установленного статуса возвращает успех без новой истории и события.

### Тестирование и результат
Проверить создание заявки; неверную категорию; запрет подмены автора, комнаты и начального статуса; изоляцию чужих заявок; доступ по ролям; фильтры; недопустимые переходы; повтор статуса; конкурентные запросы; недоступность Identity без частичного сохранения.

**Готово, когда:** жилец создаёт и видит только свои заявки, REVIEWER обрабатывает очередь; изменения сохраняются согласованно с историей.

## Этап 3. Kafka и Notifications

У Notifications нет публичных бизнес-HTTP-операций. Основной контракт — Kafka-события `issue.created` и `issue.status_changed` с UUID `eventId`.

### Задачи
- Настроить Kafka-топик `dorm.issues` и consumer group `dorm-notifications`.
- Публиковать события создания заявки и изменения статуса.
- Сохранять каждое полученное событие в `notifications_db` с уникальным `eventId`.
- Формировать сообщения о новой заявке и смене статуса и отправлять их через Telegram Bot API.
- Логировать получение, успешную обработку и ошибку отправки события.
- Сохранять `received_at`, `sent_at`, `failed_at` и текст ошибки в `notifications_db`.
- На текущем этапе не добавлять отдельные retry-политики и DLQ; ошибки должны быть видны в логах и базе.

### Тестирование и результат
Проверить оба типа событий; невалидный payload; недоступность Kafka, БД и Telegram; перезапуск consumer; повторное событие с тем же `eventId`; сохранение результата обработки и технических логов.

**Готово, когда:** штатные события сохраняются в `notifications_db` и доставляются в Telegram, а успешная и неуспешная обработка видны в логах и базе.

## Этап 4. Gateway + интеграционное тестирование

### Задачи
- Маршрутизировать `/api/v1/auth/**` в Identity.
- Маршрутизировать `/api/v1/issues` и его дочерние пути, `/api/v1/categories` в Issues.
- Согласовать префиксы без ошибочного переписывания путей.
- Передавать `X-Session-Id`; настроить CORS при необходимости.
- Не публиковать `/internal/**` и бизнес-API Notifications.
- Проверить Docker Compose, переменные окружения, healthchecks и постоянные volumes.
- Не считать Gateway единственной проверкой доступа: права проверяются бизнес-сервисами.

### Тестирование и результат
Через Gateway пройти создание аккаунта ADMIN, вход, создание заявки, получение списка, открытие деталей, обработку сотрудником, выход и получение уведомления в Telegram. Проверить недоступность внутренних путей, передачу ошибок и поведение при сбое downstream-сервиса.

**Готово, когда:** сервисы работают совместно через единую публичную точку входа, а внутренние операции недоступны клиенту.

## Этап 5. Frontend + тестирование

### Задачи
- Реализовать согласованные макеты и адаптивную вёрстку.
- Добавить вход, интерфейс создания пользователей для ADMIN, личный кабинет RESIDENT и рабочую очередь REVIEWER/ADMIN.
- Добавить список заявок с вкладками по статусам и переход на `/issues/{issueId}`.
- Передавать `X-Session-Id` в запросах и удалять его при выходе.
- При `401` возвращать пользователя на страницу входа.
- Добавить валидацию форм, фильтры, пагинацию, загрузку, пустые состояния и обработку ошибок.
- Блокировать повторную отправку формы на время запроса; не повторять автоматически создание заявки с неопределённым результатом.

### Тестирование и результат
Проверить формы и валидацию; отображение по роли; `401`, `403`, `409`, `503`; истечение сессии; повторные клики; мобильную версию. Выполнить браузерные сквозные тесты основного сценария.

**Готово, когда:** все роли выполняют свои действия через интерфейс без ручного вызова API.

## Примеры задач для доски

| Задача | Содержание | Критерий приёмки |
|---|---|---|
| AUTH: создание пользователя | Создать пользователя ADMIN с BCrypt-хешем первоначального пароля | `201`; при дубликате логина `409`; пароль не возвращается |
| AUTH: серверная сессия | Создать, проверить и отозвать UUID-сессию | Активная сессия определяет пользователя; истёкшая и отозванная дают `401` |
| ISSUES: список и детали | Разделить доступ RESIDENT и REVIEWER/ADMIN | Жилец видит свои заявки, ответственные — общую очередь; детали открываются по `issueId` |
| ISSUES: создание заявки | Проверить роль и категорию, получить проживание, сохранить заявку и историю | `201`, статус NEW; сбой Identity не оставляет записей |
| ISSUES: смена статуса | Проверить переход и `expectedStatus` в транзакции | Недопустимый переход или конфликт — `409`; повтор не создаёт историю |
| NOTIFICATIONS: обработка события | Сохранить событие, отправить Telegram, записать результат и логи | Событие видно в `notifications_db`; успешная и неуспешная отправка зафиксированы |
| GATEWAY: публичные маршруты | Настроить пути и передачу авторизации | Все согласованные операции доступны; internal не маршрутизируется |
| FRONT: список заявок | Подключить список, фильтр и пагинацию | Жилец видит свои заявки, сотрудник — очередь; ошибки и пустой список обработаны |
| DOCS: синхронизация Swagger | Уточнить роли, UUID, модели и описания; убрать примеры | Спецификации валидны и согласованы между сервисами |

Задача считается готовой, когда выполнены её критерии приёмки, добавлены необходимые тесты и обновлена затронутая документация. Для каждой задачи назначаются ответственный и статус: «К выполнению», «В работе», «На проверке», «Готово».
