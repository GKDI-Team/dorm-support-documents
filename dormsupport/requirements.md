# DormSupport

## Назначение

Система приёма заявок на устранение неисправностей в общежитии. Жилец создаёт обращение, сотрудник фиксирует ход ремонта. Уведомления поступают в закрытую Telegram-группу сотрудников. Актуальный статус и полное описание доступны в списке заявок на сайте.

## Бизнес-требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| BR-01 | Администратор выдаёт доступ жильцам и сотрудникам. | Созданы логин и роль; для жильца выбрана комната. Пользователь получает одноразовый код лично и устанавливает свой пароль. |
| BR-02 | Жилец создаёт заявку на ремонт. | Указаны название, описание, категория и место. Заявка со статусом NEW отображается в личном списке. |
| BR-03 | Сотрудник изменяет статус по мере выполнения ремонта. | Разрешены NEW → IN_PROGRESS → CLOSED. Каждый переход содержит время и автора. |
| BR-04 | Сотрудники получают уведомления в Telegram. | При создании в группу поступают номер, категория, название, краткое описание и место; при обработке - номер и переход статуса. Сбой доставки не блокирует работу с заявками. |

## Роли

| Действие | RESIDENT | REVIEWER | ADMIN |
|---|---|---|---|
| Создать пользователя, выдать код | Нет | Нет | Да |
| Создать заявку | Да | Нет | Нет |
| Смотреть заявки | Свои | Все | Нет |
| Менять статус | Нет | Да | Нет |

У пользователя одна роль. Сотрудники работают с общей очередью. Назначение исполнителя, повторное открытие и изменение текста после создания не предусмотрены.

## Интерфейс

Общее приложение с доступом по роли.

| Роль | Экран и действия |
|---|---|
| ADMIN | Форма создания пользователя: логин, имя, роль и комната для жильца. После сохранения отображаются ID, логин и автоматически созданный код первого входа. |
| RESIDENT | Форма заявки и список собственных заявок: название, категория, полное описание, место и статус. |
| REVIEWER | Список всех заявок с фильтром по статусу. В строке доступны «В работу» для NEW и «Закрыть» для IN_PROGRESS. |

Вход и активация доступны всем ролям. Перевыпуск кода до активации выполняется в разделе администратора по ID пользователя. Изменения статуса выполняются в приложении; Telegram используется для уведомлений.

## Создание аккаунта и вход

1. Администратор входит через POST /auth/login и получает JWT.
2. GET /rooms возвращает комнаты с названием и адресом корпуса.
3. POST /admin/users создаёт User, профиль Resident для жильца и ActivationCode одной транзакцией. Код формируется автоматически и возвращается вместе с созданным пользователем.
4. Администратор лично передаёт логин и код. Код - случайные 24 байта в base64url без padding, 32 символа, срок действия 24 часа.
5. POST /auth/activate проверяет код, записывает хеш пароля и погашает код атомарно.
6. Пользователь входит через POST /auth/login. JWT действует 3600 секунд; после истечения выполняется новый вход.

Первый администратор создаётся при начальном заполнении базы. Самостоятельной регистрации нет. Перевыпуск кода допустим только до активации; старый код отзывается. Восстановление пароля активированного аккаунта не входит в API.

Логин содержит 3-64 символа: строчные латинские буквы, цифры, точку, дефис и подчёркивание. Имя - 1-150 символов; пароль - 12-128. В БД хранятся хеши паролей и кодов. Вход и активация ограничиваются по частоте. JWT проверяется по подписи, сроку, issuer и audience. Пароли, токены и коды не записываются в логи. Развёртывание использует HTTPS.

## Создание и обработка заявки

1. Жилец загружает GET /categories и заполняет форму.
2. POST /issues принимает title, description, categoryId и locationDetails. Автор определяется по JWT, комната - по профилю Resident. Комната, номер, корпус и адрес фиксируются в Issue при создании.
3. Issues запрашивает место проживания через внутренний Identity API. Issue со статусом NEW и начальная IssueStatusHistory с published_at=NULL сохраняются одной транзакцией в Issues DB. После коммита клиент получает 201.
4. Publisher публикует событие из истории в RabbitMQ. Notification Service создаёт Notification в Notifications DB, отправляет сообщение и сохраняет результат.
5. Сотрудник получает очередь через GET /issues?status=NEW. Список содержит полное описание, место и статус каждой заявки.
6. PATCH /issues/{issueId}/status переводит заявку в IN_PROGRESS, затем в CLOSED. Каждая смена сохраняет Issue и историю одной транзакцией в Issues DB.
7. Жилец видит текущий статус своих заявок через GET /issues. История хранится в БД для фиксации переходов и публикации событий.

locationDetails описывает место неисправности: комнату или общее помещение своего корпуса. Поля residentId, roomId и начальный status в запросе создания не допускаются. Категории хранятся в БД: «Электрика», «Сантехника», «Отопление», «Другое».

## Статусы и параллельные изменения

Разрешены только NEW → IN_PROGRESS → CLOSED. Создание фиксирует from_status=NULL и to_status=NEW. Изменение статуса выполняется с блокировкой строки Issue.

PATCH передаёт status и expectedStatus. Если текущий статус равен status, возвращается 200 без новой истории и уведомления. Иначе несовпадение expectedStatus даёт 409 STATUS_CONFLICT; недопустимый переход - 409 INVALID_STATUS_TRANSITION. Закрытая заявка неизменна.

| № | Сущность | Назначение |

| 7 | IssueCategory | Категория неисправности |
| 8 | IssueStatus | Коды и названия статусов |

Поля и ограничения приведены в data-model.md. ERD: diagrams/erd.svg; исходник: diagrams/erd.mmd.

## Архитектура

Frontend обращается к /api/v1 через reverse proxy. /auth/*, /admin/* и /rooms маршрутизируются в Identity Service; /issues* и /categories - в Issues Service. Notification Service получает события из RabbitMQ и отправляет сообщения через Telegram Bot API.

У каждого сервиса отдельная БД PostgreSQL и собственные учётные данные. Прямой доступ к БД других сервисов запрещён.

| Сервис | БД | Таблицы |
|---|---|---|
| Identity | identity_db | User, ActivationCode, Block, Room, Resident |
| Issues | issues_db | Issue, IssueCategory, IssueStatus, IssueStatusHistory |
| Notifications | notifications_db | Notification |

Базы могут размещаться на одном сервере PostgreSQL с разными владельцами и ограниченными правами подключения. Внешние ключи действуют только внутри собственной БД. Ссылки на пользователей, комнаты и события других сервисов хранятся как идентификаторы.

Issues проверяет JWT самостоятельно по публичному ключу Identity; закрытый ключ находится только в Identity. Подпись RS256, issuer, audience и exp проверяются каждым HTTP-сервисом. Профиль жильца запрашивается через GET /internal/v1/users/{userId}/housing только при создании заявки. Внутренняя ручка требует отдельный X-Service-Token, доступна только Issues и не маршрутизируется публичным reverse proxy. Внутренний токен не передаётся браузеру.

Тайм-аут запроса Identity - 2 секунды, без автоматического повторения. При сетевой ошибке, тайм-ауте, 5xx или некорректном ответе Issues возвращает 503 IDENTITY_UNAVAILABLE без создания заявки. Если Identity отклоняет профиль жильца (403/404), Issues возвращает 403 FORBIDDEN. Номер комнаты, название корпуса и адрес сохраняются в Issue. Список и смена статуса не зависят от доступности Identity при действующем JWT.

Работают один publisher и один consumer. Источник публикации - History с published_at=NULL в Issues DB. Notification Service создаёт свой журнал по событию RabbitMQ. RabbitMQ и все БД используют постоянные volumes. Публичных бизнес-HTTP-ручек у Notification Service нет.

## HTTP API

Префикс /api/v1. Формат JSON camelCase, даты UTC ISO 8601, ID - целое число от 1 до 9007199254740991. Необъявленные поля входных JSON отвергаются, текст после trim не должен быть пустым.

| Метод и путь | Назначение |
|---|---|
| POST `/admin/users` | Создать пользователя |
| POST `/admin/users/{userId}/activation-code` | Перевыпустить код активации |
| POST `/auth/activate` | Активировать аккаунт |
| POST `/auth/login` | Войти по логину и паролю |
| GET `/auth/me` | Получить свой профиль |
| GET `/rooms` | Получить комнаты для создания жильца |
| GET `/categories` | Получить категории заявок |
| POST `/issues` | Создать заявку |
| GET `/issues` | Получить доступные заявки |
| PATCH `/issues/{issueId}/status` | Изменить статус |

Внутренняя операция: GET /internal/v1/users/{userId}/housing, только Issues → Identity. Модели запросов, ответов и ошибок: openapi.yaml и openapi.json. Список содержит все поля Issue, включая полное описание и место. История через пользовательский API не выдаётся. Список ограничен limit от 1 до 100 (по умолчанию 20) и offset от 0; порядок createdAt DESC, id DESC. RESIDENT получает только свои заявки; REVIEWER - все. ADMIN получает 403 при обращении к заявкам и категориям.

Успех: 201 при создании, 200 при чтении/входе/смене статуса, 204 после активации. Ошибка имеет тело {"code":"...","message":"..."}: 400 некорректные данные; 401 ошибка входа или JWT; 403 запрещённая роль; 404 неизвестный или недоступный объект; 409 конфликт состояния; 429 превышение частоты попыток; 500 внутренняя ошибка; 503 недоступно получение места проживания. Заявки других жильцов отсутствуют в списке RESIDENT.

Примеры:

```json
{"title":"Не работает свет","description":"Лампа не включается","categoryId":1,"locationDetails":"Кухня 3-го этажа"}
```

```json
{"status":"IN_PROGRESS","expectedStatus":"NEW"}
```

Повтор POST /issues создаёт новую заявку. При неопределённом результате клиент проверяет список перед повторной отправкой. Кнопка отправки блокируется на время запроса.

## Уведомления

Сообщения отправляются в одну закрытую Telegram-группу. Бот и CHAT_ID задаются в конфигурации. Сообщения содержат данные заявки без ссылок. Жильцы отслеживают статус на сайте.

eventId=IssueStatusHistory.id. События: issue.created для начальной истории и issue.status_changed для следующих переходов. Статусы берутся из конкретной записи истории; категории неизменны в текущем API.

Publisher раз в 5 секунд читает History WHERE published_at IS NULL в Issues DB, строит событие и публикует persistent JSON в durable exchange dorm.issues. published_at выставляется после publisher confirm и успешной маршрутизации. При сбое запись остаётся доступной для повторной публикации.

Consumer использует manual ACK и prefetch=1. После получения события создаёт Notification в своей БД: id=eventId, исходный payload и время получения. Уникальный id защищает от создания второй записи по повторному событию. Если sent_at уже заполнен, сообщение подтверждается без новой отправки. Иначе consumer вызывает sendMessage, после успеха записывает sent_at и затем ACK. Сбой после отправки до сохранения sent_at может привести к дублю Telegram.

Событие issue.created содержит title, descriptionPreview (до 500 символов), categoryName, blockName, roomNumber и locationDetails. Если описание длиннее 500 символов, descriptionPreview содержит первые 499 символов и многоточие. Полное описание сохраняется в Issue и доступно в списке. Все данные для формирования сообщения приходят в событии; обращения к Identity и Issues при доставке нет. Недоступность Notifications DB не приводит к ACK или вызову Telegram до сохранения события. Подробные события, повторы и DLQ: notifications.md. Журнал доставки через пользовательский API не выдаётся.

## Критерии приёмки

| Сценарий | Результат |
|---|---|
| Создание жильца с существующей комнатой | 201; User, Resident и ActivationCode созданы |
| Дубликат логина / неизвестная комната | 409 / 400; частичных записей нет |
| Валидная активация и повтор | 204; повтор 400 INVALID_ACTIVATION_CODE |
| Истёкший или отозванный код | 400 INVALID_ACTIVATION_CODE |
| Неверный пароль или вход до активации | 401 INVALID_CREDENTIALS |
| Подмена автора или комнаты в POST /issues | 400 VALIDATION_ERROR |
| Жилец запрашивает список | Только собственные заявки; total не включает чужие |
| ADMIN читает заявки или меняет статус | 403 FORBIDDEN |
| Создание заявки при недоступном Identity | 503; Issue и History не создаются |
| Просмотр и смена статуса при недоступном Identity | Доступны с действующим JWT |
| Создание заявки при недоступном RabbitMQ | 201; History остаётся неопубликованной |
| NEW → CLOSED | 409 INVALID_STATUS_TRANSITION |
| Повтор уже установленного статуса | 200; новой истории и события нет |
| Восстановление publisher после сбоя | Неопубликованные события передаются broker |
| Временный сбой Telegram | Повторная отправка; после лимита - DLQ |
| Повтор ранее успешно обработанного события | sent_at проверен; повторный sendMessage не вызывается |

## План работ

1. Согласование требований, модели данных и контрактов.
2. Identity: пользователи, активация, вход и справочник комнат.
3. Issues: создание, список, хранение истории, статусы и права.
4. RabbitMQ и Telegram: публикация, доставка, повторы и DLQ.
5. Сквозные проверки и подготовка демонстрации.

## Границы системы

Один корпус или несколько заранее заполненных корпусов; общая очередь сотрудников; фиксированные категории и три статуса. Отсутствуют назначения исполнителей, повторное открытие, самостоятельная регистрация, вход через Telegram, личная рассылка, лента уведомлений, редактирование справочников, refresh-token и статистика.
